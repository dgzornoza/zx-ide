# zx-ide VS Code extension

## Activation Contract

Load when reading or editing anything under `projects/vscode-extension/`, or when changing the message DTOs in `projects/shared/` that the extension exchanges with the web-client.

Code style rules live in `.ai/rules/gov-typescript-code-style.md`; this skill adds the extension-specific architecture and conventions on top of them.

## Big picture

- VS Code extension bundled with webpack (entry `src/extension.ts`). Activation is gated by `workspaceContains:.zxide.json` in `package.json`.
- Dependency injection is centralized in `src/inversify.config.ts` using Inversify; most classes are `@injectable()` and registered in the container. When you add a new command or service, bind it there.
- The extension detects the project type by reading `.zxide.json` and sets the VS Code context key `ZxIdeProjectType` in `src/core/services/features.service.ts`. That context drives feature activation.

## Core flows and services

- Commands inherit from the `Command` base, which registers the VS Code command in its constructor (`src/core/abstractions/command.ts`). Creating a command means: define the class, add its `CommandName` and `Types` symbol, and add `[Types.X, XCmd]` to `InversifyConfig.commands` (`src/inversify.config.ts`). That list binds each command and also binds it to `Types.Command`; `activate()` resolves `getAll(Types.Command)`, so every listed command is registered. The extension test `registers every command contributed in package.json` fails if a contributed command is missing.
- Webview commands (`attach-project-tiles`, `attach-project-sprites`, `attach-project-map-tileset`, `create-sprites`) extend `WebviewBaseCommand` (`src/commands/webview-base.cmd.ts`), which owns the panel lifecycle, message routing and workspace file writes. Incoming webview messages go through `dispatchMessage` (`projects/shared/bridge-messages.ts`) with one handler per `WebviewToExtensionMessage` type (`MessageHandlers` is exhaustive, so a new message fails compilation until it has a handler); each open panel is a `WebviewSession` (`src/commands/webview-session.ts`) and outgoing messages go through `session.post`, typed as `ExtensionToWebviewMessage`, so replies reach the panel that sent the request; the session releases its subscriptions when the panel closes. Never keep a single `panel` field on the command. The initial messages (`initFromExtension`, assets list) are sent only when the page posts `readyFromWebview`, never right after creating the panel. Subclasses only provide the view type, title and HTML page of the web-client entry they host.
- Messages exchanged with the web-client are typed by the DTOs in `projects/shared/` (`infrastructure.ts`, `extract-graphics/extract-graphics-dtos.ts`). Any new message goes there first, never as an ad-hoc object literal.
- `CreateProjectCmd` runs the bundled CLI (`zx-ide-cli.js`) in a terminal, writes an output JSON file, then reopens the workspace (`src/commands/create-project.cmd.ts`). The CLI bundle is copied from `../cli/dist` by webpack (`webpack.config.js`).
- Z88DK projects: after build tasks end, the extension moves `.lis/.sym/.o` files into `bin/` and emits a build report by parsing the `.map` file (`src/z88dk/services/z88dk-project.service.ts`, `src/z88dk/services/z88dk-report.service.ts`).
- Domain logic lives in pure modules that import neither `vscode` nor Inversify, only Node built-ins, `projects/shared` and relative paths: `src/z88dk/domain/` (`map-file-report.ts`: `.map` symbols and build report; `breakpoint-mapping.ts` and `lis-file-lines.ts`: C/asm breakpoint to `.lis` line mapping and what to do with each mapped pair) and `src/core/domain/generated-file-routing.ts` (workspace folder, path segments and write mode of a file generated by a webview; `splitWorkspaceRelativePath` keeps the path inside its root). Services, strategies and commands are the adapters: they read files, call these functions and talk to the VS Code API. Put new decision logic in a domain module with a Vitest spec next to it.
- Z88DK asm debugging: when `zxide.z88dk.useAsmDebug` is enabled, breakpoints are remapped from C/ASM sources to the generated `.source.lis` file (`src/z88dk/services/z88dk-asm-breakpoints.service.ts`), using the language strategies in `src/z88dk/services/z88dk-asm-breakpoints-language.strategy.ts`. The service records its own `addBreakpoints`/`removeBreakpoints` calls in `OwnBreakpointChanges` and drops those events by identity, which works whether `onDidChangeBreakpoints` fires synchronously or later (never an "updating" flag); `takeExternal` must run before the first `await` of the handler. `enable()`/`disable()` are idempotent.

## Project conventions

- **Disposables:** every long-lived object extends `Disposable` and pushes its subscriptions into `_subscriptions` (`src/core/abstractions/disposable.ts`). The Inversify `onActivation` hook subscribes disposables automatically. Every event listener you register must end up in `_subscriptions`.
- **JSONC files:** workspace file edits go through `WorkspaceHelpers.writeWorkspaceJsonFile` to preserve JSONC comments when mutating files like `.vscode/launch.json` (`src/core/helpers/workspace-helpers.ts`).
- **Array extension:** the global `groupBy` array extension is added in `src/core/helpers/array-helpers.ts`. Do not redefine or shadow it.
- **Path aliases:** use the aliases (`@core/*`, `@z88dk/*`, etc., and `externalShared/*` for `projects/shared`) configured in `tsconfig.json`, `webpack.config.js` and `vitest.config.mjs`.
- **User-visible text:** command titles and configuration descriptions come from `package.nls.json` / `package.nls.es.json`; runtime strings go through `vscode.l10n.t` with entries in `l10n/`.
- **Output and terminal:** centralized in `OutputChannelService` and `TerminalService` (`src/core/services/output-channel.service.ts`, `src/core/services/terminal.service.ts`). Reuse them for new user-facing output or terminal flows.

### Helper-only filesystem and workspace access

All filesystem and workspace-directory access **MUST** go through the helper classes in `src/core/helpers/`:

- `FileHelpers` (`src/core/helpers/file-helpers.ts`) wraps `vscode.workspace.fs.*` for files and directories: `fileExists`, `readFile`, `readFileBytes`, `readDirectory`, `writeFile`. `writeFile` logs and rethrows failures; callers must handle them (`WebviewBaseCommand.writeFiles` answers `writeFilesResultFromExtension` with `success: false` and the error). If a new filesystem operation is needed and no existing method fits, **add the method to `FileHelpers` first**; never call `vscode.workspace.fs.*` directly from command or service code.
- `WorkspaceHelpers` (`src/core/helpers/workspace-helpers.ts`) builds workspace-relative `vscode.Uri` instances and delegates the filesystem work to `FileHelpers`. Use `getWorkspaceUri(...segments)` to obtain a URI; never reach into `vscode.workspace.workspaceFolders` or call the private `findZxideWorkspaceFolder` helper from outside `WorkspaceHelpers`.

Domain-specific helpers that need filesystem access (`AssetsHelpers`, etc.) compose the two helpers above and never bypass them. This keeps the abstraction surface small, allows swapping the underlying API (for tests) and centralizes logging and error handling.

The only legitimate direct `vscode.workspace.fs.*` callers are `FileHelpers` itself and the few call sites that operate on a URI the caller already built (for example `vscode.workspace.openTextDocument`, or `vscode.workspace.fs.createDirectory` inside `WebviewBaseCommand.writeFiles`, which creates the parent directory of a write target on demand).

### File naming

- **Commands:** `.cmd.ts` suffix, and the name mirrors the VS Code command ID in kebab-case (`attach-project-tiles.cmd.ts`, `create-project.cmd.ts`). Base/abstract command classes also use `.cmd.ts` (`webview-base.cmd.ts`). Never use `-command` as a suffix.
- **Services:** `*.service.ts`. **Helpers:** `*-helpers.ts`. **Decorators:** `*.decorator.ts`. **Strategies:** `*.strategy.ts`. **Models:** `*.model.ts`.
- Always follow the naming pattern of the existing files in the same folder before inventing a new one.

## `.zxide.json` structure

The `ZxideFile` interface in `projects/shared/zxide-project.ts` defines the schema of `.zxide.json` (the CLI writes it, the extension reads it):

- `zx-ide-cli-version`: version of the CLI that created the project.
- `template-version`: version of the template the project was created from (`ZX_IDE_TEMPLATE_VERSION` in the CLI).
- `project.type`: project type (`'sjasmplus'` or `'z88dk'`).
- `project.assetsGraphicsPaths`: optional array of workspace-relative paths to graphics asset files (the CLI writes `[DEFAULT_ASSETS_GRAPHICS_PATH]`, `assets`).
- `project.graphicsDataFolderPath`: optional folder where generated graphics source files are stored (the CLI writes `DEFAULT_GRAPHICS_DATA_FOLDER_PATH`, `src/data`).

`MachineType`, `ProjectConfigurationType` and `NewProjectModel` (the JSON the CLI writes to its `--output` file, read by `CreateProjectCmd`) live in the same shared file.

## Workflows

Run every command from `projects/vscode-extension/`:

- Build/watch: `pnpm watch` (also builds the CLI via `pnpm --filter zx-ide-cli build`).
- Compile: `pnpm compile` (webpack).
- Package: `pnpm package` builds the CLI, then the webpack production bundle.
- Unit tests: `pnpm test:unit` (Vitest, `src/**/*.spec.ts`) for the pure domain modules.
- Extension host tests: `pnpm test` (`pretest` runs `compile-tests`, `compile` and `lint` first). The test build (`tsconfig.test.json`, CommonJS) does not rewrite the `@core/*`/`@z88dk/*` aliases and cannot import `projects/shared`, so code under test must import only `vscode`, Node built-ins and relative paths (for example `src/z88dk/domain/lis-file-lines.ts`, `src/core/helpers/wait-for-file.ts`, `src/commands/webview-session.ts`).
- Lint: `pnpm lint`.
- Format: `pnpm format` (Prettier, writes) / `pnpm format:check`.
- Publishing with `vsce`: always pass `--no-dependencies` (`vsce package --no-dependencies`). webpack already bundles every dependency, and the pnpm `node_modules` layout breaks the npm-based dependency scan of `vsce`.
